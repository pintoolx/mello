# Mello 黑客松錄影操作稿

你操作的是主系統，影片才是 Demo。除了開場 22 秒的全螢幕流程圖，全程直接操作主系統；文件站獨立運行，不與主系統互相導流，兩邊都不內嵌錄影。主系統不提供演出式的關卡或測試按鈕。

## Cathay Challenge 的敘事重點

Mello 對應 Enterprise AI Agents、Secure Transaction Authorization 與 Risk-aware Financial Workflow Automation。核心不是「Agent 會轉帳」，而是「企業把採購交給 Agent 後，仍能控制支出並完成對帳」。

評分投影片可見「創新性與 AI 應用」25%、「技術實作與完整性」25%、「影響力與前瞻性」20%。影片應優先交代需求如何變成採購意圖、政策如何約束執行，以及付款後財務能得到哪些證據。不要為評分增加未接通的介面。

目前若使用 `AGENT_MODE=demo`，代表固定解析器，不是自主 LLM 決策；若 `PAYMENT_MODE=mock`，代表模擬結算。交件時必須和已接通的真實能力分開說明。真實 AI 與 testnet 的啟用、驗證由後端環境及整合測試負責，不能靠前端改標籤冒充。

## 標準定位的說法

只提兩個編號：EIP-3009 與 ERC-8004。多提會稀釋敘事，也會被追問未實作的部分。

EIP-3009 是已實作的事實陳述。x402 的 EVM exact scheme 建在 `transferWithAuthorization` 上，本專案把整份授權存成憑證：`validAfter`、`validBefore`、`nonce`、EIP-712 domain、`typedDataHash`、`signatureHash`，並與 `settlementTxHash` 綁定（`Erc3009AuthorizationRecordSchema`）。可以說「授權書與付款憑證是兩份可獨立驗證的證據」。資料庫層的 `nonce` 唯一約束即取自 3009 的 nonce 語意。流程圖與講稿寫的 ERC-3009 是同一份規格，兩種稱法可以並用。

ERC-8004 只能說成對接方向，不能說成已實作。可用的掛鉤是規格自己寫的「Payments are orthogonal to this protocol and not covered here」，以及 off-chain feedback 結構裡的 `proofOfPayment` 欄位，其註解指明可放 x402 付款證明。因此說法是：8004 的 reputation registry 需要一份可驗證的付款憑證，本專案產出的正是這份憑證，且包含完整 3009 授權、settlement hash 與自有 registry 的 AUTHORIZE／FINALIZE anchor。`contracts/MelloAuditRegistry.sol` 是自己的最小實作，8004 正在標準化同一個方向。

## 錄影前

- 依 README 設定資料庫、migrate、seed，啟動 API、兩個 Seller 與前端。`npm run dev` 單獨只會啟動前端。
- 使用 1440 × 900 或 1920 × 1080，瀏覽器縮放 100%，關閉通知。
- 開場流程圖使用 [`apps/docs/public/diagrams/procurement-flow.png`](../apps/docs/public/diagrams/procurement-flow.png)（1280 × 720），與文件站「認識 Mello」同一張圖，以原始比例全螢幕呈現。
- 使用管理員私下提供的存取碼登入；不要錄到存取碼、環境變數或錢包金鑰。
- 開啟 `/app/settings` 確認公司名稱與統一編號；開啟 `/app/policy` 與 `/app/vendors` 確認單筆限額、政策白名單、認證狀態與收款地址。新版服務目錄展示「會飛分析師」與「mello資本」，部署前先依 `service-first-catalog.md` 完成目錄遷移，不要只在旁白改名。
- 正常展示設定 `MOCK_INVOICE_FAIL_ONCE=false`。若勾選需要認證，先確認該服務已有有效認證；新目錄不會自動繼承舊服務認證。沒有認證時必須取消本次認證篩選，不能把未審核服務說成已認證。
- 確認頁面「運作環境」。若是 mock，旁白稱為模擬結算；只有真正使用 testnet 且取得鏈上證據時才稱 testnet 付款。發票一律保留 SANDBOX / TEST INVOICE 提示。
- 錄影不需要重置資料庫。保留已有案件，另建這次要操作的申請即可。

### 講稿與實作的對照

- **額度與供應商白名單**：工作區可編輯的是設定頁的公司資料與發票資訊；單筆／每日額度與白名單在「採購政策」「供應商」頁唯讀，由後端管理操作設定。因此說「設定統編與發票資料，並確認額度與白名單」，不說在這裡設定額度。
- **上傳文件**：附件只隨案件保存與下載，Agent 比對服務的依據是文字需求說明，不解析文件內容。旁白改為「描述需求並上傳文件」，不要說 Agent 讀了文件。
- **匯率**：發票台幣等值使用 `DEMO_TWD_PER_USDC`（預設 32.0）的示範匯率，不是當日匯率；目前工作區畫面只顯示 USDC 金額，台幣金額保存在發票紀錄。原句「按照當日匯率計算」改為「依設定的示範匯率換算」。
- **ERC-3009 與 EIP-3009**：流程圖與講稿稱 ERC-3009，文件與程式碼稱 EIP-3009，是同一份規格，即 x402 EVM exact scheme 使用的 `transferWithAuthorization`。

## 異常與說法邊界

- 若發票失敗且出現「重試取得發票」，只重試發票，不另建採購。已有付款不能當成未付款。
- 若停在處理中或顯示連線錯誤，重新整理同一案件；不要為了畫面好看重複下單。
- 同一案件重試與相同 request key 去重已存在；跨 Agent 必須共用業務 key，相似 prompt 配新 key 不會被當成重複採購。
- 若要展示人工核准，在「付款前控制」填 0.03 USDC，送出後先停在報價確認，再按「核准此報價並繼續」。0.05 USDC 報價不會觸發 0.08 USDC 門檻。
- 「採購政策」可凍結新付款並重新整理確認持久化；在途付款不撤銷。共用存取碼不是正式使用者職務分權。
- Mock 發票不是正式電子發票，不可稱為已向財政部有效開立。
- 信用報告仍為 Demo。即使付款與雜湊存證在 Base Sepolia 成功，也不能稱為真實徵信資料。
- 未實作 ERC-8004。沒有註冊 Identity Registry、沒有寫入 Reputation 或 Validation Registry，只能說「產出的憑證可供其對接」，不可說已支援或已整合。8004 目前仍是 Draft。
- 不要提 ERC-8126 與 ERC-8196。兩份雖為 Final，但由同一組作者提出、文件僅有參考實作而無已知生產部署；且 8196 引用的是 8126，並未引用 8004，「8196 上接 8004 身分」的說法會被指出有誤。
- `INVOICE_PROVIDER=ecpay_stage` 只是設定選項，`EcpayStageAdapter` 尚未實作，bootstrap 會直接拋錯。不可展示或宣稱已串接綠界。
- 付款成功但服務未交付目前沒有退款或爭議流程。被問到時直接說明這是尚未涵蓋的範圍，不要即興描述不存在的機制。
